## 1. The standard

A mechanism must read as something an engineer could build, and the system
could measure. The fields separate the PRD (what/why), the design doc (how),
the ADR (why this choice), and validation (whether it works) — and a quality
gate refuses vague output. Verbatim from
`enrich-mechanism-spec.ts:120`: *"a mechanism is an EXECUTABLE technical causal
chain, not an explanation."*

---

## 2. The layers of a mechanism

The user's model — **Upstream → Process → Downstream + operations +
algorithm** — maps onto existing `MechanismSpec` fields:

```
            ┌──────────────── ONE MECHANISM ────────────────┐
 UPSTREAM   │   input_data[]            (what it consumes)   │
 (inputs)   │                                               │
            ├───────────────────────────────────────────────┤
 PROCESS    │   how_it_works[]          (ordered procedure)  │
 (algorithm │   runtime_flow[]          (executable spine —  │
  + ops)    │     step · component · data(in→out) · user_sees│
            │   implementation_methods[]  (compared builds)  │
            │   decision_record         (ADR — chosen + why) │
            ├───────────────────────────────────────────────┤
 DOWNSTREAM │   user_visible_behavior   (what the user sees) │
 (outputs)  │   mechanism_hypothesis.then_improves           │
            │   research_basis.validation_experiment         │
            └───────────────────────────────────────────────┘
 Cross-cutting: mechanism_of_action · active_ingredients[] ·
   system_components[] · dosage · fidelity_signals[] · kill_criteria[] ·
   quality_score (6 axes) · use_case_mode
```

The algorithm is **already a step sequence with per-step data flow** —
`runtime_flow[].data` is the "in → out" for each step. It is simply not yet
wired as a graph (see §6b).

Field definitions live in `enrich-mechanism-spec.ts`:
- `MechanismRuntimeStep` — `{ step, component, data, user_sees }` (`:137-146`)
- `MechanismImplementationMethod` (`:150-162`)
- `MechanismDecisionRecord` (`:166-175`)
- `MechanismQualityScore` — 6 axes (`:179-192`)
- `MechanismSpec` — the full interface (`:194-239`)

## 3. Generation pipeline

1. **Trigger** — on-demand when a mechanism is deepened / opened (Lab or the
   detail drawer), via `POST /api/brainstorm/item/[entityId]/mechanism-spec`.
   *This is why a freshly-generated room shows no spec yet — nothing has been
   deepened.*
2. **Enrich** — `enrich-mechanism-spec.ts` runs the LLM against the
   feature's `first_principles` / `positive_outcome` / room context.
3. **Quality gate** — the model self-scores 6 axes (`specificity`,
   `technical_depth`, `measurability`, `ui_connection`, `feasibility`,
   `failure_mode_clarity`). If **any axis < 0.6**, it regenerates **once**.
4. **Persist** — written additively to `entities.expanded_detail.mechanism_spec`
   (does not clobber the older `ExpandedItemDetail` prose/variations/scores).

## 6. Visualization plan

### 6a. Subsystems view (L2) — SHIPPED

- `components/objective/mechanism-subsystem-view.tsx` +
  `lib/objective-canvas/build-mechanism-subsystems.ts`, mounted as the 4th
  room tab (Map · Chains · Grid · **Subsystems**).
- Mechanisms cluster by `sub_category` into folder-tabbed subsystems;
  `composes_with` = **undirected** synergy links (verified symmetric in the
  generator); `interferes_with` = conflict links; + a bundle/conflict insights
  strip.

### 6b. Mechanism-internal data-flow view (L3) — TO BUILD

**Form:** a **Data Flow Diagram / computational graph** — the research match
for "upstream → process → downstream." Nodes = operations; edges = data.

**Source data:** `runtime_flow[]`. Each step already carries `component` and
`data` (in → out), so the steps wire into a directed chain:

```
 input_data[]  →  [step1: component]  →  [step2]  →  …  →  user_visible_behavior
                       │ data out ────────┘ data in
```

**The wiring fork (this is the one real rigor gap):**
- **(Fast / interim)** parse the free-text `runtime_flow[].data` "in → out"
  string heuristically to connect steps. Ships quickly; brittle.
- **(Rigorous — recommended)** enrich `enrich-mechanism-spec.ts` so each
  runtime step emits structured `produces` / `consumes` token IDs, giving an
  exact dependency graph. One additive field on `MechanismRuntimeStep`
  (`produces: string[]`, `consumes: string[]`); no DB migration (lives in the
  `expanded_detail.mechanism_spec` JSON). Existing specs regenerate on next open.
  *Recommended because the whole point of this deliverable is technical rigor;
  a parsed-string graph undercuts that.*

## 7. The "approved → subsystems / pending" process

```
 Mechanism approved  ─────────────▶  appears on the Subsystems page
 (chain edges approved /            (and, when deepened, exposes its L3
  quality gate passed)               data-flow view)

 No approved mechanism for a slot ─▶  render a PENDING placeholder
```

"Pending" applies at **two** granularities (both worth showing):
- **L2 pending** — a subsystem (sub_category) with zero approved mechanisms →
  a dashed "pending" subsystem slot.
- **L3 pending** — an approved mechanism with **no `mechanism_spec` generated
  yet** → its data-flow view shows "Deepen to generate" rather than an empty
  graph.

Approval source: the existing edge-approval flow
(`/api/brainstorm/room/edges/approve`) + the 6-axis quality gate.

## 8. Open decisions (recommendations marked ★)

1. **Pending granularity** — ★ support BOTH L2 and L3 pending (§7); they're
   complementary, not exclusive.
2. **Data-flow wiring** — ★ enrich the generator with structured
   `produces`/`consumes` step IDs (§6b) over parsing free text — rigor is the
   point.
3. **Where the L3 view lives** — ★ open it from a mechanism card in the
   Subsystems view (click a lever → its internal data-flow), keeping the
   altitude metaphor (zoom in one more level).

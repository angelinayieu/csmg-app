# Layer Definitions — what "layer" means, precisely, in each place

> Written 2026-05-28 by reading the code, not from memory. Every claim cites the
> file that defines it. The word **"layer" is overloaded across at least six
> distinct systems** in this codebase — they sit on *different axes*, at
> *different scopes*, stored in *different places*. Conflating them is the
> single biggest source of confusion. This doc pins each one down and then says
> bluntly where they collide.

---

## 0. The one-screen disambiguation table

| # | System | "A layer is…" | The layer set | Scope | Stored in | Defined in |
|---|--------|---------------|---------------|-------|-----------|------------|
| **1** | **ObjectiveStack** (objective-canvas *macro* causal stack) | A level of abstraction in the problem, from substrate→outcome, **containing variables** | 4–6 LLM-generated layers, each tagged with an *archetype* | One **objective** | `spaces.synthesis_data.objective_canvas.layers` (JSONB) | `lib/objective-canvas/layer-model.ts`, `decompose-into-layers.ts`, `decompose-prompt.ts` |
| **2** | **Room lanes** (objective-canvas *within-room* lateral lanes) | One of the room's fixed analysis stages | **pain · features · outcomes · objective** (fixed) | One **sub-objective room** | `entities.layer_ontology_id` → lane; order hardcoded | `sub-objective-room-view.tsx` (`RoomLane`), room `page.tsx` (`LAYER_ORDER`) |
| **3** | **`layer_ontology`** (per-space KG layer hierarchy) | A domain-rigorous level in the space's knowledge graph | Domain-seeded (e.g. molecular→circuit→cognitive→behavioral→performance) | One **space** | `layer_ontology` table (1 row per layer) | `types/layer-ontology.ts`, migration `20260615_layer_ontology.sql` |
| **4** | **`layer_dependencies`** (cross-layer cascades) | A directed propagation claim *between* two `layer_ontology` layers | edges, kind ∈ causal/modulatory/inhibitory/compensatory/reinforcing | One **space** | `layer_dependencies` table | `types/layer-ontology.ts`, migration `20260620_layer_dependencies.sql`, `lib/pipeline/cross-layer-cascade-prediction.ts` |

| **6** | **Dimensional layers** (`entities.layer`) | A structural scale of a system | **system · domain · thread** (+ fault, unassigned) | A system graph | `entities.layer` column | `lib/graph/layout-engine.ts` (`computeDimensionalLayout`) |
| — | **Causal-map altitudes** (Phase 12.A zoom) | A C4 zoom level (not a semantic layer) | canvas · room · item · variation | The map view | URL / view state | `components/objective/causal-map/lib/types.ts` (`Altitude`) |
| — | **`knowledge_layer`** (legacy enum, **deprecated**) | Old hardcoded KG layer | internal · conceptual · external · bridge | space | `entities` (legacy) | `types/layer.ts` — *replaced by #3* |

**Mental model in one line:** #1 is *vertical, per-objective, semantic, LLM-made*. #2 is *lateral, per-room, fixed*. #3 is *vertical, per-space, domain-scientific, persisted*. #5 is *layout-only, derived from importance*. #6 is *structural scale*. The rest are zoom levels or legacy.

## 1. ObjectiveStack — the macro causal stack (the one with "stuff inside each layer")

This is almost certainly what the question means by *"what's inside each layer, their definitions."* It is the **only** layer system where a layer literally *contains* sub-elements (variables).

**Source of truth:** `lib/objective-canvas/layer-model.ts` (types + validation), generated by `decompose-into-layers.ts` (one LLM call at the clarifying→picking transition), prompt in `decompose-prompt.ts`.

### 1.1 The shape (from `layer-model.ts`)

```
ObjectiveStack
├── domain_template   one of 6 (see §1.3)
├── template_rationale  why this template fits THIS objective
├── layers[]          4–6, ordinal 1 (bottom/substrate) → N (top/outcome)
│     ├── id            "L1".."L6"
│     ├── ordinal       1..N, contiguous, no gaps
│     ├── name          1–3 word, LLM-generated, user's vocabulary
│     ├── description   1 sentence: what this layer IS
│     ├── archetype     substrate | mechanism | process | output | outcome
│     └── variables[]   3–7 — THE CONTENTS OF THE LAYER
│           ├── id           snake_case slug
│           ├── name         display label
│           ├── description  1–2 sentences, specific to the objective
│           └── domain_tag?  optional sub-cluster ("biological", "structural")
├── influences[]      cross-layer causal arrows (see §1.4)
├── generated_at
└── state_hash        sha256(objective + clarifying answers); drives staleness
```

### 1.2 The 5 archetypes — what each layer *is by role* (from `decompose-prompt.ts` + the generic fallback in `decompose-into-layers.ts`)

The archetype is the layer's **role in the causal flow**, independent of its domain name. There are exactly five, and the prompt assigns them positionally: *substrate at L1, outcome at L_N, and mechanism + process + output for the middle.*

| Archetype | Definition (verbatim intent from the fallback descriptions) | User-actionable? |
|-----------|-------------------------------------------------------------|------------------|
| **substrate** | "Foundational inputs the user can adjust directly" — time, attention, money, environment, starting state. | Directly adjustable |
| **mechanism** | "Levers the user pulls to convert inputs into change" — the primary interventions on the substrate. | **The intervention layer** |
| **process** | "How the mechanisms execute over time" — frequency, intensity, consistency, the adaptation loop. | The workflow |
| **output** | "Observable signals the process produces" — what you track week-over-week (quant + qual). | The measured signal |
| **outcome** | "The strategic goal — what the user is ultimately optimizing." | The target (rarely directly actionable) |

> Critical note: `archetype` is an LLM judgment (temperature 0.4). The prompt itself blurs the middle ("mechanism + process + output for the middle"), so the **process vs mechanism vs output boundary is fuzzy** — treat the archetype as a hint, not a hard taxonomy.

### 1.3 The 6 domain templates (from `LayerDomainTemplate` in `layer-model.ts`)

The LLM picks **one** template per objective. The layer **names below are the JSDoc-illustrated pattern**, NOT fixed strings — for every template except `generic`, the actual `name` of each layer is **LLM-generated in the user's vocabulary**. Only `generic` has hard-coded names (it's the fallback).

| Template | When | Illustrative L1→L5 pattern |
|----------|------|-----------------------------|
| `software` | products, apps, technical systems | Infra → Data → Logic → Interface → UX |
| `cognition_health` | mental / physical / behavioral health | Foundational → Biological → Cognitive → Behavioral → Outcome |
| `business_ops` | company / team / process | Tactical → Operational → Strategic → Executive → Market |
| `behavior_change` | personal habits, identity, routines | Environment → Triggers → Routine → Goal → Identity |
| `scientific` | research, hypothesis testing, prediction | Foundations → Mechanism → Phenomenon → Application → Impact |
| `generic` | fallback | **Substrate → Mechanism → Process → Output → Outcome** (fixed) |

The **generic fallback stack** (used verbatim when the LLM call fails — `buildGenericFallbackStack`) is the canonical reference: L1 Substrate (input_resources, environmental_conditions, starting_state) → L2 Mechanism (primary_levers, supporting_systems) → L3 Process (execution_pattern, adaptation_loop) → L4 Output (measurable_signals, qualitative_indicators) → L5 Outcome (primary_outcome, secondary_outcome).

### 1.4 The 6 influence verbs — how layers connect (verbatim from `decompose-prompt.ts`)

| Verb | Meaning | Direction |
|------|---------|-----------|
| `enables` | L_n's state *allows* L_(n+1) to operate (compositional) | upward |
| `produces` | L_n's state *directly outputs* L_(n+1)'s state | upward |
| `depends_on` | L_(n+1) *requires* L_n as substrate (read upward) | upward (stated downward) |
| `constrains` | L_(n+1)'s state *limits* what L_n can do (top-down) | downward |
| `measures` | L_top *is the measurement of* L_lower (closure) | top→bottom closure |
| `aggregates` | L_(n+1) is a *rollup* of multiple L_n signals | upward |

Most influences are adjacent pairs (L_n → L_(n+1)); 1–3 long-range closures (e.g. L_N → L_1 `measures`) are encouraged where they're real.

### 1.5 How a sub-objective maps onto the stack (from `decompose-prompt.ts` JOB 3 + `layer-model.ts`)

A sub-objective proposal is tagged (by the proposer LLM) with:
- **`layer_ordinals: integer[]`** — which layers it touches (`improvement_goals.layer_ordinals`, GIN-indexed).
- **`layer_position_label: string`** — a chip computed from the ordinals (`computeLayerPositionLabel`):

| Shape (`computeLayerPositionShape`) | Ordinals | Label |
|---|---|---|
| `direct` | single | `"L3 · Direct"` |
| `bridge` | 2 adjacent | `"L2→L3 · Bridge"` |
| `span` | 2 non-adjacent | `"L1+L4 · Span"` |
| `cross_stack` | ≥3 | `"Cross-stack"` |

> Critical note: in the Phase 12.A **canvas map**, a sub-objective node is placed in the band of its **maximum** ordinal (`primaryOrdinalOf` in `causal-map/lib/graph-build.ts`) — a deliberate simplification ("its effect lands at the most emergent layer it reaches"). A bridge/span node therefore renders in one band, with its span communicated only by the chip.

## 2. Room lanes — the within-room lateral axis (pain / features / outcomes / objective)

**This is a DIFFERENT axis from the ObjectiveStack and they do not unify.** The ObjectiveStack is *vertical* (abstraction levels across the whole objective). Room lanes are *lateral* (the analysis stages **inside one sub-objective's room**).

**Source of truth:** `LAYER_ORDER` constant in `app/objective/[spaceId]/sub/[subId]/page.tsx`:

```
LAYER_ORDER = ["pain", "features", "outcomes", "objective"]
```

- The four lanes are **fixed** (slugs + order are hardcoded). Labels/colors come from the space's `layer_ontology` rows (`CANONICAL_LANE_LABELS` provides fallbacks).
- An entity is assigned to a lane via `entities.layer_ontology_id` → the matching layer's slug.
- Rendered as the room's "Variables" view (3 visible lanes — pain · mechanism · result; "objective" is the parent, shown in the header), and as nodes in the Phase 12.A **Room CLD** (`RoomItemNode`, where pain→feature→outcome are the columns).

So the objective-canvas seeds its space's `layer_ontology` (#3) with these four pain/features/outcomes/objective stages, while a scientific/pipeline space seeds the *same table* with domain-scientific stages (§3). **#2 is the objective-canvas seed of #3.**

## 3. `layer_ontology` — the per-space KG layer hierarchy

**Source of truth:** `types/layer-ontology.ts`, DDL `migration 20260615_layer_ontology.sql`.

A domain-rigorous, per-space replacement for the legacy hardcoded `knowledge_layer` enum (internal/conceptual/external/bridge). Each layer is a row:

```
OntologyLayerDefinition { ordinal, slug, label, description, color,
                          typical_node_kinds[], example_nodes? }
```

**Provenance** (`OntologySource`): `starter` (pre-built template, picked by the planner) · `research_agent` (deep-research agent generates a custom one grounded in the user's prompt + papers) · `user_authored` · `hybrid`.

**Starter templates** (seeded in the migration) are domain-scientific, e.g.:
- neuro/cognition: `molecular → circuit → cognitive → behavioral → performance/experiential`
- sleep: `circadian → autonomic/homeostatic → cognitive → behavioral`
- nutrition: `biochemistry → physiology → behavior → outcome`
- causal/scientific: `cause → mechanism → mediator → outcome`

Used by the pipeline, the twin (`twin-layer-stack-view.tsx`), and `KGNodeShape` for layer-aware rendering. **Not linked to the ObjectiveStack (#1)** — a space can have both, unrelated. (§18 of `OBJECTIVE_CANVAS_OPERATION_MAP.md` discusses a possible future unification.)

### 3.1 `layer_dependencies` — cross-layer cascades (sibling of #3)

Directed propagation claims *between* two `layer_ontology` layers (`types/layer-ontology.ts`, migration `20260620`). `LayerDependencyRow`: `from_layer_id → to_layer_id`, `kind ∈ {causal, modulatory, inhibitory, compensatory, reinforcing}`, plus `strength` (0..1), `lag_label`/`lag_hours`, `mechanism` (the load-bearing claim), `evidence_summary`, `confidence` (cascades with no edge evidence MUST be ≤0.5). Written by `cross-layer-cascade-prediction.ts`.

## 4. Layout tiers — "L1 Strategy / L2 Methods / L3 Mechanisms / L4 Atoms"

**Source of truth:** `lib/graph/layout-engine.ts` (`computeLayeredLayout`, `laneLabelsTier`).

> ⚠️ **These are NOT semantic layers.** They are *visualization bands* the "Layered" KG layout drops nodes into, derived from each entity's **importance tier** (`fundamental → L1`, `critical → L2`, `important → L3`, `moderate → L4`) — or, when importance is homogeneous, **inferred from graph topology** (BFS depth from root nodes), via `inferTiersFromTopology`. The labels Strategy/Methods/Mechanisms/Atoms are *cosmetic* names for importance bands, not a causal stack.

This is the layer system most easily mistaken for the ObjectiveStack because "Mechanisms" appears in both. They are unrelated: #1 is an LLM causal decomposition of an objective; #5 is a render-time importance sort of a graph.

---

## 5. Dimensional layers — system / domain / thread

**Source of truth:** `entities.layer` column + `computeDimensionalLayout` in `lib/graph/layout-engine.ts`.

A **structural scale** decomposition for hierarchical system graphs:
- `system` — "Systems (3D blocks)" — the top composite
- `domain` — "Domains (2D surfaces)" — mid-level groupings
- `thread` — "Threads (1D lines)" — the leaf-level lines of work
- (+ `fault`, `unassigned`)

Children are placed under their parent via `composes`/`has_component` edges. This is about *part-of nesting scale*, not abstraction level or importance.

## 6. Things called "layers" that aren't semantic layers

- **Causal-map altitudes** (Phase 12.A): `canvas · room · item · variation` — C4 **zoom levels** (`Altitude` in `causal-map/lib/types.ts`). The map renders one altitude at a time; these are not contents-bearing layers.
- **Evaluation tiers** (adjacent concept): `heuristic · rubric · evidence · ensemble · simulated · tested` — the 5/6-rung **method-confidence ladder** (`MethodBadge`). Sometimes spoken of as "layers of rigor" but they're tiers, not layers.

## 7. Critical assessment — where this bites

1. **"layer" is dangerously overloaded** (≥6 systems). Worse, **"mechanism" appears in five unrelated places**: an ObjectiveStack *archetype* (#1), a `layer_ontology` *stage label* (#3 scientific seed), a layout *tier* ("L3 Mechanisms", #5), a room edge's `agent_feedback.mechanism`, and `layer_dependencies.mechanism` (#4). When code/PRD/agent says "the mechanism layer," it is genuinely ambiguous which of these it means. **Recommendation:** in prose + agent prompts, always qualify — "ObjectiveStack mechanism archetype" vs "graph mechanism tier" vs "room mechanism lane."

2. **Two unconnected vertical stacks coexist per space.** The ObjectiveStack (#1, in `synthesis_data` JSONB, per-objective, LLM-made) and `layer_ontology` (#3, in its own table, per-space, domain-scientific) are *both* "substrate→outcome-ish vertical layerings" and are **not linked**. A `cognition_health` ObjectiveStack and a `molecular→...→performance` layer_ontology describe overlapping reality with different vocabularies and no join. This is the strongest candidate for future unification (see §18 of the operation map).

3. **ObjectiveStack names + archetypes + verbs are LLM output, not ground truth.** Only the `generic` fallback has fixed layer names. Archetype assignment and influence verbs are temperature-0.4 judgments; the prompt admits the middle archetypes blur. Don't build logic that assumes a fixed name like "L3 = Cognitive."

4. **Room lanes (#2) ≠ ObjectiveStack (#1).** They are orthogonal axes (lateral within-room vs vertical across-objective) that happen to both be persisted partly via `layer_ontology`/JSONB. A sub-objective sits at *one or two* ObjectiveStack ordinals (vertical) **and** its room internally has all four pain/features/outcomes/objective lanes (lateral). Don't try to map lane → ordinal.

5. **Canvas-map placement is a heuristic.** `primaryOrdinalOf = max(layer_ordinals)` means a bridging sub-objective renders in a single band; the "span" is only legible via the chip. Documented, intentional, but a known simplification.

## 8. Quick "which layer do I mean?" decision guide

- *Talking about an objective decomposed into abstraction levels with variables inside?* → **ObjectiveStack (#1)**.
- *Talking about pain/features/outcomes inside one room?* → **Room lanes (#2)**.
- *Talking about a space's persisted, domain-scientific KG levels (molecular, circuit…)?* → **`layer_ontology` (#3)**, cascades between them → **#4**.
- *Talking about how the KG graph is laid out in horizontal bands by importance?* → **Layout tiers (#5)** — render-only.
- *Talking about system → domain → thread nesting?* → **Dimensional (#6)**.
- *Talking about zooming canvas→room→item?* → **Altitudes** (not a semantic layer).
